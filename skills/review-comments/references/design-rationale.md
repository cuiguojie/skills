# 设计依据与取舍记录

供维护或扩展本 skill 使用，记录来源、适用性判断与任务边界。

## 来源与改编边界

设计起点是 antirez 的 [Writing system software: code comments.](https://antirez.com/news/124)。核心保留的是注释承载代码无法表达的知识、保护修改约束，以及写不清说明可能暴露实现问题的观察。

以下针对 AI 辅助开发的取舍是本包的设计判断。Agent 可以按需查看实现和类型，重复解释普通流程的收益因此降低；能读懂行为仍不等于能确认业务理由和长期契约。

## 原有分类的处理

| 类别或实践 | 当前决定 | 原因与落点 |
| --- | --- | --- |
| Function comments | 保留契约，收窄覆盖要求 | 类型外的保证有价值；无需给所有函数补说明，也不以减少跳转为充分理由。 |
| Design comments | 保留背景和取舍 | 可以由 ADR 或设计文档承载；源码只留必要局部约束，不强制文档索引。 |
| Why comments | 核心保留 | 业务理由与兼容性约束通常不能从实现恢复，但必须有依据。 |
| Teacher comments | 有条件保留 | 通用教学可按需解释；特殊变体、证明要点和难以重建的不变量仍有价值。 |
| Checklist comments | 保留非显然修改约束 | 关注实际依赖，不把所有调用关系变成文字清单。 |
| Guide comments | 移除默认添加要求 | 阅读节奏属于情境与风格选择；缺少不算缺陷，准确现有标题也不自动删除。 |
| Trivial comments | 保留冗余判断 | 用信息增量判断，不以 what/why 标签、长度或数量机械判定。 |
| Debt comments | 保留提醒用途 | TODO 可作为个人工作流的持久入口；更新过期事项，不为整洁隐藏未解决问题。 |
| Backup comments | 保留清理判断 | 确认是旧实现备份后再处理，排除示例和工具指令。 |
| 状态快照 | 收窄为复杂状态的例外 | 容易漂移的逐行镜像不默认添加；正确性验证确有需要时仍可保留。 |
| 通过解释发现漏洞 | 保留为诊断方式 | 说明与路径不一致时追踪具体反例，但不据此自动开展完整代码 review。 |

## 任务边界的依据

现有注释提供明确的检查对象；缺失注释检测需要更广的代码理解与背景调查。因此一致性检查只审查已有注释，并在有限取证不足时保留不确定性。这控制了调查成本，但不保证发现所有维护信息缺口。

consistency-check.md 是自足的日常任务指南，只检查事实陈述与代码是否一致。comment-principles.md 保存更广的质量判断，包括冗余与表达价值，供维护和扩展时使用，不在日常检查中加载。分类表中的保留项不代表当前任务会执行所有检查。若扩展其他任务，应保持判断标准一致，由入口选择任务，彼此不递归触发。

## 后续验证方向

用真实局部变更检查三种边界：注释引用已移除的符号时指出具体冲突；准确但冗余的流程说明不作为一致性问题报告；并发承诺存在具体疑点且无法局部核实时标记待确认而不断言错误。授权修改后再独立审查同一片段，观察是否出现无依据的反复增删。

以上场景尚未进行独立行为评测。
