# 注释判断原则

以下标准用于判断注释的信息价值。具体检查范围和修改权限由任务指南决定。

## 信息价值

注释优先写 why：补充代码本身看不出的背景、约束和取舍。不要把代码做了什么再解释一遍；必要的接口契约和复杂不变量除外。不要猜测设计理由。

区分代码当前的行为、必须维持的保证和选择该实现的原因。实现通常能证明行为，不能独自证明业务动机或长期承诺。

| 信息 | 判断标准 |
| --- | --- |
| 业务例外、外部限制、兼容性要求 | 关注适用条件和误改后果；理由需有需求、协议、记录或用户确认支持。 |
| 设计选择与取舍 | 保存实际约束、接受的代价及适用边界；不根据当前结构虚构曾比较过的方案。 |
| 接口契约 | 类型未表达的单位、所有权、失败后状态或幂等性可能值得说明；命名、类型或已有文档已表达的信息无需重复。 |
| 顺序要求与关联修改 | 非显然的依赖及回归条件有维护价值；可直接从普通调用关系确认的流程无需全部转写。 |
| 算法与状态说明 | 特殊变体、正确性条件和容易误改的不变量可以保留；通用算法教学、逐行状态镜像和省去普通代码跳转不是默认要求。 |
| 引导与阶段说明 | 尊重项目已有风格。缺少标题不构成缺陷；已有准确标题也不因偏好简洁而必须删除。 |
| TODO、FIXME 与限制 | 是待处理事项的入口，不是当然应清除的噪声。区分已确认的问题与待确认的疑问，尽量保留明确的后续动作。 |
| 注释掉的旧实现 | 确认属于备份后才建议移除；不要误判示例、许可证、平台说明或工具指令。 |

## 表达方式与证据

- 命名、类型、接口文档和设计文档都可能满足信息需求。沿用项目的注释格式，避免重复已有表达。
- 完整决策背景适合设计文档；源码保留理解和安全修改当前位置所需的约束。局部提醒与设计文档有少量必要重叠可以接受。
- 现有注释是待核对的陈述，不是正确性的证据。代码与注释矛盾时，可能是代码缺陷，也可能是注释过期；不能默认改注释使其迎合错误实现。
- 无法确认不等于错误。尤其对并发、性能、安全性等承诺，应说明证据范围；不能因为局部代码不足以证明，就建议删除承诺或断言作者编造。
- “没有具体帮助”需从实际内容判断。仅复述语法且不携带契约、背景或约束的注释可视为冗余；注释长、解释 what 或采用某种格式，本身都不是问题。
- 不以数量或分类覆盖率评价质量。只提出值得采取行动的问题；缺少信息必须关联具体的错误调用或危险修改，表达偏好不进入整改清单。
